# What belongs in the repo

Three categories. Getting one wrong is the most common cause of a broken build or a
change that silently disappears after deploy.

## 1. In git — the build fails or misbehaves without these

| Path | Notes |
|---|---|
| `composer.json` | |
| `composer.lock` | Must be in sync with `composer.json`. The build may run `composer validate --check-lock`. |
| `app/etc/config.php` | The module list. See `config-php.md`. |
| `app/code/`, `app/design/`, `app/etc/` (rest) | Your own modules and themes. |
| `pub/` entry points, `.htaccess`, `index.php` | Whatever your repo normally carries. |

Optional, honoured if present:

| Path | Effect |
|---|---|
| `config.php.build` (repo root) or `app/etc/config.php.build` | Themes, scopes, build-time system config. **Frequently not in git** — luroConnect commonly maintains it on the server instead, and a server-side copy overwrites a committed one. Its absence is normal. See `config-php.md`. |
| `vendor_patches/*.patch` | Applied to `vendor/` after `composer install` (`patch -p0`, falling back to `-p1`). The supported way to patch a third-party package. |
| `vendor_extras/` | Its contents are copied over `vendor/` after patching. Use sparingly. |
| `magepack.config.js` | Used when magepack bundling is enabled for your environment. |

## 2. Generated by the build — must be gitignored

The build produces these. If they are committed, you get stale artifacts, huge diffs
and merge conflicts, and in some cases a build that packages the wrong thing.

```
vendor/
generated/
pub/static/*
var/
pub/media/
```

Also generated, and containing credentials — these must never be committed:

```
auth.json     # written at build time from the composer credentials luroConnect holds
id_rsa        # the transfer key, written at build time
```

`var/view_preprocessed` is a special case: the build relocates it out of `var/` so it
ships inside the release, because `var/` becomes a symlink to shared storage on the
server. You do not need to do anything about this — just don't commit `var/`.

## 3. Injected at deploy time — never in git

| Path | Where it comes from |
|---|---|
| `app/etc/env.php` | The server's environment overlay. Holds DB, Redis, search, crypt key, cache config. **The build deletes any `env.php` it finds**, so committing one achieves nothing except leaking secrets. |
| `pub/media` | A symlink to a directory shared across all releases. |
| `var` | Symlinked to shared per-environment storage. |
| `pub/errors/` | luroConnect's maintenance and error pages, unpacked over whatever the release contained. |

Media is shared deliberately: uploaded images must survive a deploy and a rollback.
Anything the build ships under `pub/media` is copied into the shared directory when
the release is first unpacked, and never removed from it afterwards — so treat
committed media as add-only, and don't expect deleting a file from the repo to delete
it from the live site.

## A working `.gitignore`

`gitignore.sample` in the kit contains this. Merge it into your existing
`.gitignore`; do not blindly replace yours.

```gitignore
/vendor/
/generated/
/var/
/pub/media/
/pub/static/*
!/pub/static/.htaccess
/app/etc/env.php
/auth.json
/id_rsa
/.env
```

Note what is deliberately **absent**: `app/etc/config.php` and
`app/etc/config.php.build`. Several public Magento `.gitignore` templates ignore
`app/etc/config.php`. On luroConnect that would break the build — the module list
would be empty.

If `config.php` is currently ignored in your repo, fix it with:

```bash
git check-ignore -v app/etc/config.php     # shows which rule is ignoring it
# remove or negate that rule in .gitignore, then:
git add -f app/etc/config.php
```

## Checking an existing repo

```bash
git ls-files --error-unmatch app/etc/config.php       # must succeed
git ls-files config.php.build app/etc/config.php.build  # may be empty - see config-php.md
git ls-files app/etc/env.php auth.json id_rsa         # must print nothing
git ls-files vendor generated pub/static var pub/media | head   # must print nothing
git check-ignore -v vendor generated pub/static var pub/media   # must match a rule each
composer validate --no-check-all --no-check-publish --check-lock
```

If generated files are already committed, remove them from the index without deleting
them locally:

```bash
git rm -r --cached vendor generated pub/static var pub/media
# add the ignore rules above, then commit
```

## Branches

luroConnect builds a specific branch per environment (typically one branch for staging
and one for production), configured on our side. A build always builds the tip of that
branch — merge your work into it, then build. If you need a different branch built,
that is a configuration change on the luroConnect side; ask us.

The release is identified by the **abbreviated git commit id** of that branch tip.
That is what appears in the deploy dropdown and what you pass as `release` to the
deploy API.
